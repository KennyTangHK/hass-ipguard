# Protocol notes and verification limits

This independent beta project supports the IPGUARD Android app protocol (`com.noralsy.portaphone`). These notes describe message shapes and client behavior; continued compatibility with the vendor's live service requires field testing.

The API library implements this sequence:

1. Connect a ZeroMQ DEALER with an installation UUID to `tcp://zmq.campiserveur.com:5579`, send the Android greeting, and request phone/email verification with `sp_srv_check_auth`.
2. Validate the six-digit code using `sp_srv_validate_auth`, then obtain a server public key through `sp_srv_ask_key`.
3. Connect to `tcp://zmq.campiserveur.com:5577` using fresh client CURVE keys and the returned server key. Send the initial secure greeting before `sp_srv_check_username`. Use `sp_srv_override_username` only after explicit replacement consent.
4. Receive and acknowledge `srv_sp_update`, retain the activation credential at `data[1].sip_pwd`, and receive `bc_sp_relays` inventories. Reset notices during pending enrollment are ignored; an activated-installation reset requires reauthentication.
5. Receive `ps_sp_sdp_offer` on the current activated secure connection. Validate the bounded token, remote identity, sender and Base64 SDP, suppress repeated token digests, and emit a sanitized incoming-call callback. With media explicitly enabled, retain the same call's offer privately until demand or expiry. Receipt sends no call acknowledgement, answer, pickup or hangup.
6. On an explicit media claim, accept one complete answer for that call and send `sp_ps_sdp_answer` to the preserved offer route with its exact token and remote identity. Concurrent or duplicate submissions do not retransmit it. Incoming termination and connection changes invalidate the call. No provider acknowledgement, pickup or hangup is generated by this path.
7. Send `sp_brd_open_door` with a one-based relay number and board routing identity only when the current inventory permits remote release. Match `brd_sp_open_door_ack` by token and board sender. A missing acknowledgement is an unknown outcome and is never replayed automatically.

Direct enrollment uses ordinary TCP before the CURVE channel. It is not HTTPS or encrypted onboarding. Saved authorization includes identifiers, UUID, verification code, server key and activation credential; do not share serialized sessions or Home Assistant's private storage.

Only remote-capable relay types are exposed. Bluetooth-only access and pending badge confirmation do not create usable cloud controls. No proven cloud physical door/lock-state event was established, so buttons do not report open/closed or locked/unlocked state. Firebase, audio pickup, microphone, refusal/hangup controls and SIP media are outside this library's implementation. Incoming notifications and media answers reuse the existing MQ connection; WebRTC decoding and RTSP output belong to the companion rather than this SDK.

Automated tests use synthetic accounts and loopback plaintext/CURVE servers. Disposable Home Assistant containers have external networking disabled. Live account acceptance, credential lifetime, account aliases, simultaneous mobile installations, incoming call delivery without mobile push, and a supervised physical release remain field checks.
